# 第19章 デバッグとテスト

Piet のプログラムは、思ったとおりに動かないことがよくあります。しかも、普通の言語のように「何行目で何のエラー」と教えてくれることはまずありません。1 コーデルの塗り間違いで、出力が少し違う、何も出力されない、いつまでも終わらない、といった症状が出るだけです。

本章では、Piet のプログラムの誤りを見つけて直すための道具と考え方をまとめます。npiet と piet.py のトレースの読み方、トレース画像、よくあるバグとその症状、そして誤りを未然に防ぐためのテストの書き方です。

!!! abstract "この章で学ぶこと"
    - npiet の `-t` と piet.py の `-t` が出力するトレースの読み方
    - npiet のトレース画像（`-tpic`）で実行経路を目で見る方法
    - Piet スタジオのステップ実行とブレークポイント
    - Piet でよく起きるバグ 6 種類の症状・原因・直し方
    - 無限ループへの対処（`-e` によるステップ数の制限）
    - 入力と期待される出力を使った回帰テストと、処理系どうしの差分テスト

## 19.1 Piet のバグはなぜ見つけにくいのか

Piet の誤りが見つけにくい理由は、主に 3 つあります。

1. **エラーが起きない**。仕様は「実行できない命令は無視して次へ進む」と定めています。スタックが空なのに `add` を実行しても、何も起きずに先へ進みます。誤りがあっても、その場では何の兆候もありません。
2. **プログラムの「意味」が見た目と一致しない**。色ブロックの境界やコーデル数は、画像を眺めただけでは正確に読み取れません。隣り合った同じ色が 1 つのブロックにつながっていても、人間の目にはそれが分かりにくいのです。
3. **実行の経路が見えない**。どのブロックからどのブロックへ移ったのかは、DP と CC の状態と、ブロックの形で決まります。少し形が違うだけで、経路がまったく変わることがあります。

対策の基本は、**実行の様子を記録して、意図と比べる** ことです。そのための道具がトレースです。

## 19.2 トレースを読む

### npiet のトレース

npiet に `-t` を付けると、1 ステップごとに次のような記録を出力します。次の図のプログラムは 65（`A`）を出力するつもりで描いたものです（19.5 節で詳しく扱います）。

@piet ch19/size_bug caption="A を出力するつもりが 2 を出力してしまうプログラム" zoom=32

```text
$ npiet -q -t size_bug.png

trace: step 0  (0,0/r,l lR -> 4,0/r,l nR):
action: push, value 7
trace: stack (1 values): 7

trace: step 1  (4,0/r,l nR -> 5,0/r,l nB):
action: duplicate
trace: stack (2 values): 7 7

trace: step 2  (5,0/r,l nB -> 6,0/r,l lM):
action: multiply
trace: stack (1 values): 49

trace: step 3  (6,0/r,l lM -> 7,0/r,l nM):
action: push, value 1
trace: stack (2 values): 1 49
...
```

1 つのステップは次の 3 行からなります。

- `trace: step 0  (0,0/r,l lR -> 4,0/r,l nR):` ― ステップ番号（0 から数える）、移動元のコーデルの座標と DP・CC・色、移動先のコーデルの座標と DP・CC・色。DP は `r`（右）・`d`（下）・`l`（左）・`u`（上）、CC は `l`（左）・`r`（右）です。色は明度（`l` 淡い・`n` 通常・`d` 濃い）と色相（`R` 赤・`Y` 黄・`G` 緑・`C` シアン・`B` 青・`M` マゼンタ）の 2 文字で表されます。
- `action: push, value 7` ― 実行した命令。
- `trace: stack (2 values): 7 7` ― 実行後のスタック。**先頭（トップ）から順に** 並んでいます。本書の表記（左が底）とは逆なので注意してください。

ステップ 0 で `push, value 7` となっているのが手がかりです。作者は 8 を積むつもりだったので、ここで誤りがあると分かります。

白を通過したときは、`trace: white cell(s) crossed - continuing with no command at 7,0...` のような行が出て、そのステップでは命令が実行されません。

### piet.py のトレース

本書の piet.py の `-t` は、同じ情報を日本語で 1 行にまとめて、標準エラー出力に書きます。

@trace ch19/size_bug

こちらはブロックの色を日本語で書き、移動元のブロックの大きさをかっこの中に示します。スタックは本書の表記どおり左が底です。黒や画像の端に止められた試行は、字下げした行で「どこで止められ、CC と DP をどう変えたか」が示されます。push の値はブロックの大きさそのものなので、「淡赤(7)」と表示された時点で、淡赤のブロックが 7 コーデルしかないことが分かります。

!!! tip "トレースはファイルに保存して検索する"
    長いプログラムのトレースは数万行になります。`npiet -q -t prog.png > trace.txt 2>&1` のようにファイルに保存し、`grep -n "action: out" trace.txt` で出力命令だけを抜き出す、`grep -n "stack (0 values)\|is empty" trace.txt` でスタックが空になった場所を探す、といった使い方が効果的です。

## 19.3 トレース画像で経路を見る

GD ライブラリと libpng を有効にしてビルドした npiet は、実行の経路を画像に描き込む **トレース画像** を作れます。

```sh
npiet -q -tpic -tpf 32 prog.png     # npiet-trace.png が作られる
```

| オプション | 意味 |
|---|---|
| `-tpic` | トレース画像 `npiet-trace.png` を作る |
| `-tpf <n>` | 1 コーデルを何ピクセルに拡大して描くか |
| `-tps` | DP・CC の情報を省いた簡略版にする |
| `-ts <n>` / `-te <n>` | トレースを描き始める／描き終えるステップ |

次の図は、19.5 節で直した後の「A を出力する」プログラムのトレース画像です。

@img ch19/trace-size_fix.png caption="npiet -tpic によるトレース画像。矢印が移動の経路、文字が実行した命令を表す"

線は各ステップでどのコーデルから出て、どのコーデルへ入ったかを示し、その横に実行した命令（`push(8)`、`dup` など）が書き込まれます。コーデルの中の小さな文字は、そのブロックで試した DP と CC の組です。

ループや分岐を含むプログラムでは、トレース画像の効果がさらに大きくなります。次の図は、第17章のアセンブラで作ったループのプログラム（19.5 節のバグ 6 の修正版）のトレース画像です。白い配線を通って画像を一周し、ループの先頭へ戻ってくる様子がよく分かります。`noop` と書かれた線は、白を滑って命令を実行しなかったステップです。

@img ch19/trace-loop_fix.png caption="ループするプログラムのトレース画像。noop は白を通過したステップ"

トレース画像は、ステップ数が多いと線が重なって読めなくなります。`-ts` と `-te` で、調べたい範囲のステップだけを描くようにしましょう。

## 19.4 Piet スタジオでデバッグする

トレースは強力ですが、文字の記録を読むだけでは、プログラムのどこを実行しているのかを画像と結び付けにくいことがあります。本書の Piet スタジオ（[第2章](ch02.html)）は、トレースと同じ情報を、画像の上で直接確かめられるように作られています。

@img ch19/studio-break.png caption="Piet スタジオでループの先頭にブレークポイントを置き、3 回目に止まったところ"

上の図は、19.5 節のバグ 6 で扱うループのプログラム（修正版の `loop_fix`）を開き、ループの先頭の淡赤のコーデルに **ブレークポイント** を置いて実行した画面です。デバッグに使う機能は次のとおりです。

| 操作 | 働き |
|---|---|
| 1 ステップ（F10） | 1 回の遷移だけ実行し、画面を更新する |
| 再生（F6） | 「再生の速さ」のつまみで決めた速さで、1 ステップずつ続けて実行する。もう一度押すと一時停止 |
| 実行（F5） | 停止するかブレークポイントに達するまで、全速で実行する |
| リセット（F2） | 最初の状態に戻す。入力欄を書き換えたときも自動でリセットされる |
| 右クリック | そのコーデルにブレークポイントを置く（もう一度右クリックで外す） |

ブレークポイントは、**そのコーデルを含む色ブロックに入った時点** で実行を止めます。上の図では、実行（F5）を 3 回押して、ループの先頭に 3 回目に入ったところで止まっています。出力欄には 9 と 7、状態の欄には「ステップ 41　DP 右　CC 左　位置 (7,7)」と「スタック [5]」が表示されています。ループを 1 周するごとにスタックの値が 2 ずつ減っていく様子を、F5 を押すたびに確かめられるわけです。

画面右下のトレースの欄には、piet.py の `-t` と同じ形式の記録が流れます。白の中で進めずに向きを変えた試行（「白の中で進めない: …」）も表示されるので、白い配線の中でどう曲がったかも追えます。キャンバスの上でマウスを動かすと、下の状態表示に、そのコーデルの座標・色・ブロックの大きさが表示されます。19.5 節のバグ 1 やバグ 2 のような「ブロックの大きさの食い違い」は、これで直接確かめるのがいちばん早い方法です。

!!! tip "どこにブレークポイントを置くか"
    ループの先頭、条件分岐の直前（`pointer` を実行するブロック）、出力命令の直前のブロックが、ブレークポイントを置く代表的な場所です。「この場所に来たときのスタックは、設計どおりか」を確かめる、という使い方をします。来るはずの場所で止まらなければ、経路そのものが設計と違っていることが分かります。

## 19.5 よくあるバグ

ここからは、Piet で実際によく起きる誤りを 6 つ取り上げます。どれも数コーデルの小さな例ですが、大きなプログラムで起きる誤りも、ほとんどがこのどれかに当てはまります。

### バグ 1: ブロックの大きさの数え間違い

先ほどの「A を出力する」プログラムです。65 = 8 × 8 + 1 として、8 コーデルの淡赤のブロック（4×2 の長方形）から始める設計でした。ところが、長方形の右下の 1 コーデルを塗り忘れたため、淡赤のブロックは 7 コーデルになり、7 × 7 + 1 = 50、つまり文字 `2` が出力されてしまいました。

@grid ch19/size_bug

直したものが次の図です。

@piet ch19/size_fix caption="淡赤のブロックを 8 コーデルに直した版。A を出力する" zoom=32

@grid ch19/size_fix

**症状**: 出力される数や文字が少しだけ違う。
**見つけ方**: トレースで push の値を確かめる。piet.py のトレースでは、ブロックの大きさがかっこ内に出る。
**対策**: 大きなブロックは、数えやすい長方形（4×2、5×5 など）にする。長方形の一部を欠けさせない。

### バグ 2: 同じ色のブロックがつながる

3 と 2 を足して 5 を出力するつもりのプログラムです。下の段に飾りのつもりで赤のコーデルを 1 つ置いたところ、それが真上の赤のブロックと接してしまいました。

@piet ch19/merge_bug caption="飾りの赤が上の赤のブロックとつながり、5 ではなく 6 を出力する" zoom=32

@grid ch19/merge_bug

4 近傍で接した同じ色のコーデルは、1 つのブロックになります。赤のブロックは 2 コーデルではなく 3 コーデルになり、`push` の値が 3 に変わって、3 + 3 = 6 が出力されます。飾りを取り除けば 5 を出力します。

@piet ch19/merge_fix caption="飾りを取り除いた版。5 を出力する" zoom=32

**症状**: push の値が意図より大きい。ブロックの出口が意図と違う場所になり、経路そのものが変わることもある。
**見つけ方**: トレースで push の値やブロックの大きさを確かめる。画像編集ソフトの「塗りつぶし」で色を一時的に変えると、どこまでがひとつながりかが一目で分かる。
**対策**: 同じ色のブロックどうしを隣接させない。命令に関係しない部分に色を置くときは、周囲と違う色にするか、黒で区切る。

### バグ 3: CC による出口の取り違え

次のプログラムは、C 字形の赤のブロック（7 コーデル）から、その右下にある濃赤のブロックへ出て `push 7` を実行し、7 を出力するつもりで描かれています。

@piet ch19/cc_bug caption="C 字形のブロックの右上から出てしまい、何も出力しない" zoom=32

@grid ch19/cc_bug

ところが、赤のブロックの右端の列には、上端 (2,0) と下端 (2,2) の 2 つのコーデルがあります。DP が右、CC が左のとき、出口は右端の列の **上端** です。そこには飾りの黄のコーデルがあり、インタプリタは赤から黄へ移って `add` を実行してしまいます（スタックが空なので無視されます）。その後は白を滑って濃赤に入り、`out(number)` もスタックが空なので無視されて、何も出力せずに終わります。

@trace ch19/cc_bug

直し方は、右上の黄を黒に変えることです。すると最初の試行は黒に止められ、CC が右に切り替わって、右端の列の **下端** から濃赤へ出られます。

@piet ch19/cc_fix caption="右上を黒にした版。CC が切り替わり、下端から出て 7 を出力する" zoom=32

19.3 節と同じ方法で作ったトレース画像を見ると、最初の試行で止められ、下端のコーデルから出ていることが分かります。

@img ch19/trace-cc_fix.png caption="修正版のトレース画像。赤のブロックの下端から濃赤へ移っている"

**症状**: 経路が意図と違い、思わぬ命令が実行される。
**見つけ方**: トレースで、移動元・移動先の座標を確かめる。トレース画像で経路を目で追う。
**対策**: 出口になりうるコーデル（各縁の両端）の隣を意識して設計する。迷ったら、長方形のブロックを使う。

### バグ 4: 白のすき間で命令が消える

5 を出力するつもりのプログラムですが、濃赤と淡マゼンタのブロックの間に、白のコーデルが 1 つはさまっています。

@piet ch19/gap_bug caption="白のすき間のせいで out(number) が実行されず、何も出力しない" zoom=32

白を通過した移動では、命令は実行されません。したがって、濃赤から淡マゼンタへの移動に対応するはずだった `out(number)` が実行されず、何も出力されません。npiet のトレースでは、そのステップに `action` の行がなく、代わりに `white cell(s) crossed` と表示されます。

**症状**: ある命令だけが実行されない。
**見つけ方**: トレースで白の通過を探す。
**対策**: 命令をつなぐブロックどうしは、必ず直接接するように描く。白はあくまで「命令を実行しない通り道」として意図的に使う。

### バグ 5: 色の変化を逆向きに数える

7 から 2 を引いて 5 を出力するつもりのプログラムです。`subtract` は「色相 1 段・明度 1 段」の変化ですが、作者は移動の **先から元へ** の向きで数えてしまいました。

@piet ch19/reverse_bug caption="変化の向きを逆に数えたため、subtract の代わりに out(char) が実行される" zoom=32

淡赤から濃マゼンタへの変化は、正しく「元から先へ」数えると色相 5 段・明度 2 段で、`out(char)` です。そのため、先頭の 2 が文字コード 2 の制御文字として出力され、続く `out(number)` がスタックに残った 7 を出力します。出力は「目に見えない文字 + 7」になります。

@trace ch19/reverse_bug

@piet ch19/reverse_fix caption="正しい向きで数えた版。淡赤 → 黄で subtract になり、5 を出力する" zoom=32

**症状**: 意図と違う命令が実行され、出力やスタックが大きく狂う。
**見つけ方**: トレースの `action` を、設計時の命令の列と 1 つずつ照らし合わせる。
**対策**: 色相・明度の変化は必ず「今のブロック → 次のブロック」の向きで数える。命令から次の色を決めるときは、表を使って機械的に求める（[付録A](appA.html)）。

### バグ 6: 終わらないループ

最後は制御の誤りです。9 から 2 ずつ減らし、0 になったら止まるつもりのループですが、9, 7, 5, 3, 1, −1, … と奇数を数え続け、0 にはなりません。

```pasm
  push 9
loop:
  dup
  outn
  push 10
  outc
  push 2
  sub
  dup
  jnz loop      ; 0 にならないので永久に回る
  pop
```

@piet ch19/loop_bug caption="0 にならずに回り続けるループ" zoom=8

条件を「0 でない間」から「0 より大きい間」に変えれば、正しく止まります。

```pasm
  dup
  push 0
  gt            ; n > 0 なら 1
  jnz loop
```

@piet ch19/loop_fix caption="「0 より大きい間」繰り返すように直した版" zoom=8

**症状**: いつまでも終わらない。出力が止まらない、あるいは何も出力しないまま固まる。
**見つけ方**: ステップ数を制限して実行し、トレースの最後の部分を見る（次節）。
**対策**: ループの終了条件は「ちょうど 0」より「0 以下」「0 未満」のように幅を持たせる。

## 19.6 無限ループへの対処

終わらないプログラムを調べるときは、実行するステップ数に上限を設けます。

```sh
npiet -q -e 500 loop_bug.png             # 500 ステップで打ち切る
python3 tools/piet.py run -e 500 loop_bug.png
```

npiet は上限に達すると `error: configured execution steps exceeded (500 steps)` と表示して終了します。`-t` と組み合わせ、トレースの末尾を見れば、ループのどこを回っているのかが分かります。

!!! warning "timeout コマンドで止めると出力が消えることがある"
    npiet は標準出力をバッファリングしています。無限ループするプログラムを `timeout` コマンドや Ctrl+C で強制終了すると、バッファに溜まっていた出力が書き出されずに失われることがあります。「何も出力されない」と見えても、実際には出力していた、ということがあるのです。調査には `timeout` ではなく `-e` を使いましょう。

意図せず「止まらない」原因は、ループの条件の誤りだけではありません。

- 停止のしかけ（周囲を黒で囲んだブロック）のつもりが、どこか 1 か所すき間があって外へ出てしまう。
- 白の領域で、色のブロックへ戻る道がない（白の中を回り続ける）。npiet の既定の動作では、白の中の同じ経路の再走査を検出しないので、仕様上は停止するはずのプログラムでも止まりません（[第16章](ch16.html)、[付録C](appC.html)）。

## 19.7 テストを書く

一度動いたプログラムも、手を加えるうちに壊れることがあります。特に Piet では、見た目を整えるためにブロックの形を変えただけで、意味が変わってしまうことがあります。そこで、普通のソフトウェア開発と同じように **回帰テスト** を用意しておきます。

本書のサンプルは、すべて次の形式のテストを持っています。

```text
samples/ch19/size_fix.txt     プログラム（テキスト格子）
samples/ch19/size_fix.out     期待される出力
samples/ch18/gcd.mini         プログラム（Mini 言語）
samples/ch18/gcd.in           入力 1
samples/ch18/gcd.out          入力 1 に対する期待される出力
samples/ch18/gcd.in2          入力 2
samples/ch18/gcd.out2         入力 2 に対する期待される出力
```

`tools/samples.py` は、各プログラムをすべての入力で実行し、出力が期待どおりかを調べます。

```sh
$ python3 tools/samples.py ch19
ok  ch19/cc_bug (6x5, 3 steps) out=''
ok  ch19/cc_fix (6x5, 2 steps) out='7'
...
ok  ch19/loop_fix (44x21, 97 steps) out='9\n7\n5\n3\n1\n'
--- 14 ok, 0 NG
```

本章の「バグのあるプログラム」も、**バグのある出力を期待値として** テストに登録しています。たとえば `merge_bug.out` の中身は `6` です。これは「誤りの再現」が意図どおりであることを保証するためです。もし処理系の変更でこの出力が変われば、本文の説明が正しくなくなったことにすぐ気づけます。

テストの入力は、次の観点で選ぶと効果的です。

- **典型的な値**: 普通の入力（例: 最大公約数なら 12 と 18）。
- **境界の値**: 0、1、ループが 1 回も回らない値、ループがちょうど 1 回だけ回る値。
- **入力の終わり**: 入力が空のとき、最後に改行がないとき。
- **大きな値**: 途中の計算が大きくなる値（処理系の整数の大きさの違いが出やすい）。

終わらないことが正しいプログラム（たとえば `loop_bug`）には、`.flags` ファイルに `noterm` と書き、一定のステップ数で打ち切った出力どうしを比べます。

## 19.8 処理系どうしで比べる

samples.py は、piet.py の出力と npiet の出力も比べます。2 つの独立した処理系が同じ出力を返せば、プログラムが特定の処理系の癖に依存していないことの、よい証拠になります。逆に食い違ったときは、次のどちらかです。

1. 一方の処理系に誤りがある。
2. プログラムが、仕様の解釈が分かれる部分に依存している。

本書のプログラムで 2 が起きやすいのは、負の数の除算・剰余、0 による除算、失敗した `roll`、文字の入出力（バイト単位か Unicode か）、白の中で閉じ込められた場合の停止です。これらの違いは[付録C](appC.html)にまとめました。移植性の高いプログラムを書くには、これらの部分を避けるのがいちばんです。

!!! column "コラム: デバッグのチェックリスト"
    動かない Piet のプログラムを前にしたら、次の順に確かめましょう。

    1. コーデルサイズは正しく認識されているか（`-cs` を明示して実行してみる）。
    2. 最初の数ステップのトレースは設計どおりか（push の値、命令の名前）。
    3. 同じ色のブロックがつながっていないか。
    4. 命令をつなぐブロックの間に白がはさまっていないか。
    5. 不規則な形のブロックで、出口のコーデルが意図どおりか。
    6. 停止のしかけは、8 回の試行がすべて失敗する形になっているか。
    7. 処理系に依存する命令（負の数の `mod` など）を使っていないか。

## まとめ

- Piet の誤りはエラーとして現れないので、トレースで実行の記録を取り、意図と比べる。
- npiet の `-t` はステップごとの座標・DP・CC・色・命令・スタック（先頭から順）を出力する。piet.py の `-t` はブロックの大きさも示す。
- `-tpic` のトレース画像は、経路を目で追うのに役立つ。`-ts` と `-te` で範囲を絞る。
- よくあるバグは、ブロックの大きさの数え間違い、同色ブロックの連結、CC による出口の取り違え、白のすき間、色の変化の向きの取り違え、ループの終了条件の誤り。
- 無限ループは `-e` でステップ数を制限して調べる。`timeout` での強制終了は出力が失われることがある。
- Piet スタジオでは、ブレークポイントと 1 ステップ実行で、画像の上で実行の様子を確かめられる。
- 入力と期待される出力の組で回帰テストを作り、別の処理系との差分テストも行う。
