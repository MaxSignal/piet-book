# 付録C 仕様の曖昧な点と処理系ごとの違い

Piet の仕様は短く、多くの細部を処理系に任せています。作者の David Morgan-Mar 自身、権威ある処理系を定めておらず、仕様についての質問には「あなたがいちばん筋が通ると思うやり方で」と答えてきたと書いています。その結果、同じ画像でも処理系によって動作が変わる場合があります。

この付録では、そうした「解釈が分かれる点」を整理し、仕様の記述、npiet 1.3h、本書の piet.py（と、同じ設計の Piet スタジオ・ブラウザ版ビューア）、そして動作の方針を文書化している Pietron の 4 つを比べます。npiet の動作は、ソースコード（npiet.c）を読んだうえで、小さなテストプログラムを実際に実行して確かめました。Pietron については、そのリポジトリの説明によります。

以下、主な項目を詳しく見ていきます。

## C.2 除算と剰余

仕様は `mod` について「結果は除数と同じ符号になる」と明記し、2017 年の注記で「5、2、−1、−4 を 3 で割った余りはすべて 2」という例を示しています。これは床除算（商を負の無限大の方向へ丸める）の余りと一致します。`divide` の丸め方は書かれていませんが、`mod` と整合させるなら床除算が自然です。

npiet は C 言語の `/` と `%` をそのまま使っているため、どちらも 0 の方向へ丸めます。次のプログラムで確かめられます。

```pasm
; -7 mod 3 と 7 mod -3
  push -7
  push 3
  mod
  outn
  push 32
  outc
  push 7
  push -3
  mod
  outn
```

@piet ch20/spec_mod caption="負の数の mod。仕様どおりなら「2 -2」、npiet では「-1 1」" zoom=10

| 式 | 仕様（piet.py） | npiet 1.3h |
|---|---|---|
| −7 mod 3 | 2 | −1 |
| 7 mod −3 | −2 | 1 |
| −7 ÷ 2 | −4 | −3 |

**移植性のための指針**: 負の数を `divide` や `mod` に与えないように書きましょう。たとえば「n が奇数か」を調べるときは、n が負になりうるなら、先に絶対値を取るか、十分大きな偶数を足してから `mod` を使います。

## C.3 0 による除算

仕様は 0 による除算の扱いを処理系に任せ、2014 年の追記で「単に命令を無視することを推奨する」としています。npiet は 2004 年の変更以来、2 つの値を取り出したうえで、目に見える値として 99999999 を積みます（`-w` を付けると警告も出します）。

@piet ch20/spec_divzero caption="7 を 0 で割ってから 2 回出力する。piet.py は「0 7」、npiet は「99999999 」" zoom=10

piet.py では除算が無視され、スタックには 7 と 0 がそのまま残るので、2 回の `out(number)` で「0」と「7」が出力されます。npiet では 99999999 が 1 つ残るだけなので、2 回目の出力はスタック不足で無視されます。

## C.4 roll の失敗と値の切り詰め

仕様は「負の深さはエラーであり、命令は無視される」と定めています。piet.py は「無視」を「スタックを一切変えない」と解釈し、深さと回数の 2 つの値も取り出しません。npiet は、まず 2 つの値を取り出してから深さを調べ、負または深すぎる場合は回転だけを行いません。

@piet ch20/spec_roll caption="深さ -1 の roll の後でスタックを出力する。piet.py は「1 -1 2 1」、npiet は「2 1 」" zoom=8

この違いは、`roll` の深さを計算で求めるプログラムで問題になります。深さが負になったり、スタックの大きさを超えたりする可能性があるなら、`roll` の前に値を確かめましょう。

npiet の `roll` には、もう 1 つ注意点があります。スタックそのものは C の `long`（64 ビットの Linux では 64 ビット）の配列ですが、`roll` で値を回転させるとき、回数が正なら先頭の値を、負なら区間の最も深い値を、`int`（32 ビット）の一時変数にいったん入れて動かしています。そのため、32 ビットに収まらない値がその位置にあると、上位のビットが失われます。

```pasm
; 1 と 2^32 + 5 を積み、swap（深さ 2 の roll）してから両方を出力する
  push 1
  push 256
  dup
  mul
  dup
  mul          ; 2^32
  push 5
  add          ; 4294967301
  swap
  outn
  push 32
  outc
  outn
```

@piet ch20/spec_bigroll caption="2^32 + 5 を swap する。piet.py は「1 4294967301」、npiet は上位ビットが落ちて「1 5」" zoom=10

`swap` や `pick` のように `roll` を多用するプログラムでは、この影響が思わぬところに現れます。第III部の階乗のプログラムを npiet で実行すると、13! が正しい 6227020800 ではなく 1932053504 と出力されます（6227020800 を 32 ビットで切り詰めた値です）。

## C.5 負の値の switch

仕様は、`switch` に負の値を与えた場合について「その絶対値の回数だけ CC を切り替える」と定めています。piet.py はそのとおりに動きます。npiet 1.3h の `switch` は `for (i = 0; i < val; i++)` という形で切り替えを繰り返すため、値が負だとループが 1 回も回らず、CC はまったく変わりません（値は取り出されます）。`pointer` の負の値（反時計回り）は npiet でも正しく扱われるので、違いが出るのは `switch` だけです。

**移植性のための指針**: `switch` には 0 以上の値を与えましょう。−1 で切り替えたいときは、代わりに 1 を使えば、仕様上も npiet でも同じ結果になります。

## C.6 文字の入出力

仕様は文字を Unicode として扱うとしています。piet.py は入力を文字列として受け取り、`in(char)` で 1 文字（Unicode の符号位置）を読み、`out(char)` で Unicode の文字を書きます。

npiet は C の `getchar()` で 1 バイトを読み、その値を 255（0xff）で割った余りを積みます。UTF-8 の日本語は 1 文字が複数バイトなので、1 回の `in(char)` では先頭の 1 バイトしか読めません。また、255 の余りを取るため、値 255 のバイトは 0 になります（これは不具合と考えられます）。`out(char)` も値の下位 8 ビットを 1 バイトとして書くので、255 を超える値は別の文字になります。

@piet ch20/spec_utf8 caption="文字コード 12354（あ）を出力する。piet.py は「あ」、npiet は 12354 の下位 8 ビット 0x42 にあたる「B」" zoom=6

@piet ch20/spec_inchar caption="1 文字読んでその文字コードを出力する。入力「あ」に対し piet.py は 12354、npiet は UTF-8 の先頭バイトの 227" input="あ" zoom=10

一方で、npiet のこのバイト単位の動作を逆手に取った作品もあります。遠藤侑介さんの Piet のクワインは、自分自身の GIF 画像をバイト列として出力します（[第20章](ch20.html)）。

**移植性のための指針**: 文字の入出力は ASCII（0〜127）の範囲にとどめると、どの処理系でも同じ結果になります。

## C.7 入力のプロンプト

npiet は、`in(number)` や `in(char)` を実行するたびに、標準出力に `? ` というプロンプトを出力します。対話的に使うときは便利ですが、出力をファイルに保存したり、ほかの処理系と比べたりするときには邪魔になります。`-q` を付けると表示されなくなります。本書でテストに npiet を使うときは、常に `-q` を付けています。

```sh
$ echo 5 | npiet spec_inchar.png        # -q なし
? 53
$ echo 5 | npiet -q spec_inchar.png
53
```

## C.8 規定外の色とコーデルサイズ

仕様は、20 色以外の色（オレンジ、茶色など）を使ってもよいとし、その効果を処理系に任せています。最も単純なのは白と同じに扱うこと、別の可能性は黒と同じに扱うこと、と書かれています。npiet は既定で白とみなし、`-ub` で黒、`-uu` でエラーにします。

JPEG 形式の画像は、圧縮のために色がわずかに変わり、規定外の色だらけになってしまいます。Piet のプログラムは、必ず PNG や GIF などの可逆圧縮の形式で保存しましょう。

コーデルサイズの推定方法も、仕様にはありません。npiet は画像の行と列を走査し、最も短い同色の連続をコーデルサイズとみなします。piet.py は、同色の連続の長さすべての最大公約数を使います。ほとんどの画像では同じ結果になりますが、確実を期すなら `-cs` で明示しましょう。

## C.9 白ブロック

白の扱いは、仕様の中で最も解釈が揺れてきた部分です。2008 年 1 月 25 日に「白ブロックの振る舞いの明確化」が追加され、次のことが定められました。

- 白の中で黒や画像の端に止められたら、CC を切り替え、DP を時計回りに 1 つ回して、滑り直す。
- 白の中で同じ経路をもう一度たどり始めたら、出口はないので実行を終了する。

npiet の歴史を見ると、1.1（2009 年）で遠藤侑介さんのパッチによってこの動作が実装され、1.2（2010 年）で処理が書き直されています。現在の 1.3h の既定の動作では、白の中で止められると、その白のコーデルにいったん留まり（命令のないステップとして数えられる）、次のステップでそこから 8 回まで、CC と DP を同時に変えながら進める方向を探します。同じ経路の再走査は検出しないので、白の中を回り続ける形のプログラムは停止しません。`-v11` を付けると、1.1 の動作（再走査の検出あり）になります。

@piet ch16/whiteloop caption="5 を出力した後、白い回廊に閉じ込められる。piet.py と npiet -v11 は停止し、npiet の既定の動作では止まらない" zoom=24

また npiet には、古い Perl 製の処理系の動作をまねる `-dpbug` オプションもあります。公式のサンプル集の Towers of Hanoi は、この動作に依存していると npiet の変更履歴に記されています。

**移植性のための指針**: 白の領域は「まっすぐ通り抜ける」か「黒に当たって 1 回曲がる」程度の使い方にとどめ、白の中で行き止まりになる形は避けましょう。停止は、白ではなく、色ブロックを黒で囲む形で作るのが確実です。

## C.10 整数の大きさ

仕様は、スタックの値を概念上は無制限の整数とし、あふれは処理系依存の実行時エラーとしています。npiet はスタックを C の `long` の配列で持ち（64 ビットの Linux では 64 ビット）、あふれの検査は見当たりません。ただし C.4 で見たとおり、`roll` で動かす値は 32 ビットに切り詰められることがあるので、実質的に安全なのは 32 ビットに収まる値です。Pietron は符号付き 64 ビットで、あふれると折り返すと説明しています。piet.py は Python の整数を使うので、メモリが許す限りいくらでも大きな値を扱えます。階乗のように急激に大きくなる計算では、処理系によって結果が変わる可能性があります。

## C.11 移植性の高いプログラムのために

以上をまとめると、どの処理系でも同じように動くプログラムを書くための指針は次のとおりです。

1. `divide` と `mod` には 0 以上の数だけを与える。0 で割らない。
2. `roll` の深さが負や深すぎる値にならないようにする。
3. 文字の入出力は ASCII の範囲にとどめる。
4. npiet で動かすときは `-q` を付ける。
5. 色は規定の 20 色だけを使い、可逆圧縮の形式で保存する。コーデルサイズは明示する。
6. 白の中で閉じ込められる形を作らない。停止は黒で囲んだ色ブロックで行う。
7. `switch` に負の値を与えない。
8. 32 ビット（約 ±21 億）に収まらない値を扱わない（npiet の `roll` で壊れるため）。

本書のサンプルは、この付録で違いを示すためのもの（`.flags` に `nonpiet` と記したもの）を除き、すべて piet.py と npiet の両方で同じ出力になることを確かめています。
